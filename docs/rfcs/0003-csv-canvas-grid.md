# RFC-0003:CSV 表格视图(canvas 渲染 + WASM 解析)

- 状态:已实现
- 关联:[Spec-0002](../specs/0002-csv-grid-render.md)、[Story-0002](../stories/0002-view-csv-sheet.md)

## 动机

Excel 切片目前只能给出「这是个 xlsx,有几个工作表」的摘要,用户看不到内容。
本期把它推进到**能真正看到表格**。范围刻意收窄到 **CSV**:

- CSV 是最简单的表格载体,**没有**公式、样式、数字格式、图表 ——
  正好让我们把精力放在「渲染管线」和「大数据量下的性能」这两件真正的难点上;
- 渲染管线一旦立住,后续接 xlsx 时视图层几乎不用改,只需换数据源。

**明确不做**(本期):公式求值、数字/日期格式化、图表、编辑与写回、多工作表。

## 约束

来自 `instruction.md` 的硬性要求:

1. Web 端必须用 **canvas** 绘制表格,不能用 DOM 表格;
2. 文件解析、列切分等重 CPU 逻辑必须放在 **Rust/WASM** 侧。

## 开源方案调研

### 一、CSV 解析

| 方案 | 许可证 | 体积 / 依赖 | wasm 兼容 | 维护活跃度 | 评估 |
| --- | --- | --- | --- | --- | --- |
| **`csv` 1.4(BurntSushi)** | Unlicense OR MIT | ~5K SLoC,依赖 `csv-core`/`memchr`/`itoa`/`ryu` | ✅ `wasm32-unknown-unknown` 上 std 可用,只要不碰 `from_path` | 累计约 2 亿次下载,Rust 事实标准 | **选用** |
| `csv-core` | Unlicense OR MIT | no_std,零分配状态机 | ✅ 最佳 | 同上(同一作者/仓库) | 更省体积,但要自己实现引号状态机之外的记录组装与**行号跟踪**;收益不抵风险 |
| JS 侧 `papaparse` / `d3-dsv` | MIT / ISC | 需额外打包进前端 | — | 活跃 | ❌ 违反「重 CPU 放 WASM」的硬约束 |
| Polars / Arrow 的 CSV reader | MIT / Apache-2.0 | 极重 | ⚠️ | 活跃 | ❌ 为了读 CSV 背一整套列式引擎不划算 |

**结论:直接复用 `csv` crate**,不自己写解析器。引号包裹、`""` 转义、字段内嵌换行、
CRLF/LF 混用这些坑它都趟过了,而且 `Error::position()` 能给出**出错行号**,
正好满足「错误可定位」的要求。我们只在它之上补两件它不管的事:
**编码探测**与**分隔符嗅探**。

### 二、文本编码

| 方案 | 许可证 | 说明 |
| --- | --- | --- |
| **`encoding_rs` 0.8** | (Apache-2.0 OR MIT) AND BSD-3-Clause | Firefox 在用的编码转换库,覆盖 GBK/GB18030/Big5/Shift_JIS 等;纯 Rust,wasm 友好 |
| **`chardetng` 1.0** | Apache-2.0 OR MIT | 同为 Mozilla 出品的编码**探测**器,与 `encoding_rs` 配套 |
| 自己按字节分布猜 | — | ❌ 中文编码的误判率很难做低,没必要重造 |

**结论:`encoding_rs` + `chardetng`**。中文环境里 Excel 另存的 CSV 默认是 GBK,
不处理就是满屏乱码 —— 这是必须解决的真实问题,不是锦上添花。

### 三、canvas 表格渲染

| 方案 | 渲染方式 | 许可证 | 评估 |
| --- | --- | --- | --- |
| [glide-data-grid](https://github.com/glideapps/glide-data-grid) | canvas | MIT | 能力最接近,但 React 专用且带 `lodash`/`marked`/`react-responsive-carousel` 等 peer 依赖,体积明显;数据源模型面向「按需回调取单元格」,与我们「窗口批量取数」的 WASM 边界不完全契合 |
| [canvas-datagrid](https://github.com/TonyGermaneri/canvas-datagrid) | canvas | BSD-3-Clause | 零依赖、体积最小,但主线发布停在数年前,维护活跃度存疑 |
| [RevoGrid](https://github.com/revolist/revogrid) | DOM 虚拟滚动 | MIT + 商业 Pro | ❌ 不是 canvas,直接违反硬约束;且合并单元格/公式等在 Pro |
| [FortuneSheet](https://github.com/ruilisi/fortune-sheet) | canvas + DOM | MIT | ❌ 是完整在线电子表格(工具栏、公式引擎),远超本期范围,属于「超纲功能」 |

**结论:自研一层轻量渲染管线**,理由:

1. **数据源形态不同**:我们的数据在 WASM 线性内存里,视图层通过「矩形窗口批量取数」
   访问。现成库的数据源接口都假设数据在 JS 侧,套进来反而要加一层适配;
2. **需求面窄**:本期只需要只读渲染 + 滚动缩放,不需要编辑、拖列、分组、树形;
   引入一个通用库要背上大量用不到的代码;
3. **管线可控**:分层离屏、脏矩形增量、几何纯函数可单测 —— 这些正是本次的评估重点,
   自研才能把边界划清楚;
4. 真正通用的部分(CSV 解析、编码探测)**已经复用了成熟实现**,自研只落在这一薄层视图上。

## 方案

### 分层

```
web/src/apps/excel/          视图层
  ExcelPage.tsx              页面:上传 / 状态 / 元信息
  SheetCanvas.tsx            交互:尺寸自适应、滚轮/键盘/拖拽、无障碍
  grid/geometry.ts           几何(纯函数):布局、可见区域、命中判定、滚动条
  grid/layers.ts             绘制:单元格层 / 表头 / 覆盖层
  grid/renderer.ts           调度:rAF 合并、离屏分层、滚动位图平移
  grid/labels.ts theme.ts    列名缓存 / 视觉常量
web/src/apps/shared/         复用:SheetHandle 接口、useCsvFile、logger
web/src/wasm/                WASM 封装 + 解析 Worker
crates/wasm/                 绑定层(薄)
crates/core/csv + sheet      解析与表格模型(平台无关,可原生单测)
```

### 跨边界数据流

解析要在 Worker 里(否则大文件冻住 UI),取数要**同步**(否则掉帧),
两个诉求分处不同线程,于是拆成两段:

```
Worker:parseCsvPacked → 解析 + 列切分 + 列宽度量 → 移出紧凑缓冲
   └── postMessage(transfer,零拷贝) ──▶
主线程:WasmSheet.fromPacked → 表格常驻 WASM 内存 → window() 同步取可见区域
```

表格内容**不会**以 JS 字符串数组的形式整体存在;每帧只跨边界取一屏单元格,
并在 JS 侧缓存,滚动时不重复取。

### 渲染管线

`数据 → 几何 → 裁剪 → 绘制`,单帧内的多次状态变更合并为一次 `requestAnimationFrame`。

**为什么是三张堆叠的 canvas 而不是一张**:表格里三类内容的变化频率相差两个数量级 ——
单元格(最贵,很少变)、行列头(便宜,滚动时变)、hover/选中(最便宜,鼠标一动就变)。
挤在一张画布上,鼠标划过表格就要重画上千个单元格。拆成三张互相独立的 DOM canvas 后:

- 谁变了只画谁 —— hover 只碰最上面那张几乎空白的 overlay;
- **叠加交给浏览器合成器用 GPU 完成**,主线程不再每帧做一次全视口的 `drawImage` 合成。

**滚动为什么几乎不用画**:单元格层是一块比可见区域四周各大 256 设备像素的**瓦片**。
只要滚动没超出这圈余量,就只改一下 CSS `transform` —— 平移由 GPU 完成,
主线程一个像素都不画;滚出余量才重新锚定,并用位图平移复用重叠部分、只补新露出的窄带。

渲染器内部统一用**设备像素**坐标,好处是位图平移永远是整像素、网格线永远压在像素中心。

画布尺寸也必须按设备像素对齐:后备像素与显示尺寸**同源换算**(先把后备像素向下取整到
整设备像素,再由它反推 CSS 显示尺寸)。否则容器的小数宽度乘上小数 dpr
(浏览器缩放、125%/150% 显示缩放)得不到整数,浏览器会把整块位图重采样,画面整体发虚。

## 取舍

| 决定 | 理由 |
| --- | --- |
| 短行右侧补空单元格 | 视图始终是规整矩形,不会错位;与「照实展示不规整 CSV」并不冲突 |
| 完全空白的行跳过 | 与 `csv` crate / pandas / csvkit 默认一致 |
| 列宽用「半角字符数」估算而非精确测量 | 精确测量要遍历全部单元格并调用 `measureText`,百万行不可接受;估算值取实测最坏情况,宁宽勿窄 |
| 行数/列数超限截断而非报错 | 打不开不如打开一部分,并在界面上明确标注 |
| 二进制内容直接拒绝 | 单字节编码能把任意字节硬解成字符,不拦住就是一屏乱码 |
| Worker 失败才降级主线程 | 解析失败是文件的问题,重试只是白跑一遍并污染日志 |
| 滚轮语义抽成纯函数 `grid/input.ts` | `deltaMode` 三种模式、触控板双轴、Shift 横滚、Ctrl 缩放的组合埋在事件回调里只能靠手点验证,抽出来才能单测 |
| 单元格层用**超出视口的瓦片 + transform**,而不是「画布正好等于视口 + 每帧补窄带」 | 补窄带仍要主线程每帧绘制;瓦片让绝大多数滚动帧的绘制开销归零,代价只是多一圈画布内存 |
| 瓦片余量取 256 设备像素 | 太小则频繁重锚失去意义;太大则每次重锚要画的面积与显存都涨。256 在常见行高下约 10 行,够覆盖连续滚动的绝大多数帧 |
| `will-change: transform` 只加在单元格层 | 该属性会让元素常驻显存;只有这一层真的会被 transform,其余两层不需要 |
| 事件打在一张透明的 `div` 上,画布一律 `pointer-events: none` | React 管交互与无障碍语义,渲染器管像素,两边互不干扰;也不必关心哪一层在最上面 |
